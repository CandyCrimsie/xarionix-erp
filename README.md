# XarionixERP

**XarionixERP** — это комплексное программное решение, которое объединяет ключевые бизнес-процессы компании в единую информационную среду.

## Границы доступа к адресному каталогу

`AddressType`, `AddressObject`, `Building` и `Entrance` образуют общий физический
каталог установки. Право `addresses.manage @ COMPANY` в текущем контракте
разрешает изменять этот глобальный каталог из выбранного company context.

`Location` относится к конкретной компании. Получение и изменение помещений,
технических описаний и связанных с ними данных всегда ограничивается текущим
`X-Company-Id`.

`addresses.manage @ COMPANY` также разрешает управлять глобальным справочником
типов адресов. Интерфейс явно предупреждает об этом влиянии на все компании.
Системные типы защищены, а пользовательский тип нельзя удалить, пока он
используется адресными объектами.

## Иерархия и территории

Новые объекты проверяются по типу родителя. Обычный город, посёлок или село
нельзя неявно вложить в другой населённый пункт. Районы и округа могут содержать
другие административные уровни, территории и улицы, но не здания напрямую.

Для микрорайонов, кварталов, СНТ, ТСН, ДНТ и других планировочных территорий
используется категория `territory`. Только `territory` и `thoroughfare` могут
содержать здания. Территория может содержать здание напрямую либо улицу со
зданиями. Земельный участок остаётся отдельным будущим доменом и не моделируется
как `Building`.

Существующие ранее допустимые строки не переписываются. Простое переименование
такой строки разрешено; новые перемещения и смена типа проходят актуальную
валидацию иерархии.

До внедрения Alembic startup выполняет только аддитивную совместимость
development schema: если PostgreSQL enum `address_type_category` уже существует,
в него идемпотентно добавляется значение `territory` до синхронизации базовых
типов. `create_all()` сам по себе существующий enum не изменяет.

## Поиск адресов

Интеллектуальный поиск использует PostgreSQL-расширение `pg_trgm`. При запуске
API выполняется идемпотентная команда `CREATE EXTENSION IF NOT EXISTS pg_trgm`
до создания таблиц. Пользователь PostgreSQL должен быть владельцем базы либо
иметь право `CREATE` в ней; в стандартном `docker-compose.yml` база создаётся
этим же пользователем. Если политика production-базы запрещает это право,
администратор должен один раз выполнить команду от привилегированной роли.

Поиск выполняется непосредственно в PostgreSQL поверх существующего recursive
CTE и единой `UNION ALL`-выборки адресных объектов и зданий. Элементы ответа
имеют discriminator `kind`: `address_object` содержит поле `object`, а
`building` — поле `building`; общее поле `full_address` доступно для обоих
типов. Номер дома, корпус и строение сравниваются точно; нечёткое сопоставление
применяется только к текстовым токенам длиной не менее пяти символов. Поэтому
страна, город, территория или улица находятся даже без дочерних зданий.

Это намеренное изменение структуры элементов `items` у существующего endpoint
`GET /api/v1/addresses/search`: внутренний Angular-клиент обновлён, а внешним
клиентам, которые ожидали в `items` плоский `BuildingResponse`, нужно выбирать
ветку результата по `kind`. Параметры endpoint и оболочка пагинации не менялись.

Воспроизводимый план для 105 000 тестовых зданий можно получить после запуска
тестового PostgreSQL:

```bash
docker exec -i xarionix_postgres_test \
  psql -U xarionix_test -d xarionix_test \
  < tests/performance/address_search_explain.sql
```

Скрипт сравнивает прежний contains-only запрос с новым структурированным
поиском через `EXPLAIN (ANALYZE, BUFFERS)` и использует только временные таблицы
в откатываемой транзакции.

## Тесты

Для локального запуска поднимите изолированные PostgreSQL и Redis, установите
зависимости и запустите `pytest`:

```bash
docker compose -f docker-compose.test.yml up -d
python -m pip install -r requirements-dev.txt
python -m pytest
docker compose -f docker-compose.test.yml down
```

По умолчанию тесты подключаются к PostgreSQL на `127.0.0.1:55432` и Redis на
`127.0.0.1:56379`. Для CI адреса можно переопределить переменными
`TEST_POSTGRES_*`, `TEST_REDIS_*` или полной строкой `TEST_DATABASE_URL`.

GitLab CI описан в `.gitlab-ci.yml`: job `python-tests` запускает весь набор
тестов с отдельными service-контейнерами PostgreSQL и Redis и публикует JUnit
отчёт в интерфейсе GitLab.

## Карта адресов и Yandex Tiles API

Картографическая интеграция состоит из трёх изолированных частей:

1. FastAPI проверяет JWT, `X-Company-Id` и `addresses.read`, выдаёт
   краткоживущую подписанную ссылку `/api/v1/map/session` и возвращает GeoJSON
   зданий только для текущего viewport через `/api/v1/map/buildings`.
2. Браузер загружает MapLibre динамически при открытии карты. Ключ Yandex API
   в JavaScript, HTML и ответах FastAPI отсутствует.
3. Отдельный Nginx-контейнер `map-proxy` проверяет подпись и координаты тайла,
   читает дисковый cache и только при cache miss обращается к фиксированному
   origin `tiles.api-maps.yandex.ru`. Общий limiter применяется после cache
   lookup и по умолчанию ограничивает весь proxy значением 28 RPS.

Для включения карты задайте одинаковый `MAP_TILES_SIGNING_SECRET` длиной не
менее 24 символов для API и proxy (поддерживается URL-safe Base64 с padding
`=`), добавьте `YANDEX_TILES_API_KEY`, установите
`MAP_TILES_ENABLED=true`, затем запустите инфраструктуру:

```bash
docker compose up -d --build
```

Начальная область общей карты настраивается backend-переменными и передаётся
клиенту вместе с краткоживущей map-session:

```ini
MAP_DEFAULT_LATITUDE=55.7558
MAP_DEFAULT_LONGITUDE=37.6176
MAP_DEFAULT_ZOOM=10
```

Широта ограничена диапазоном `-90..90`, долгота — `-180..180`, масштаб —
`0..20`. Значения по умолчанию показывают Москву с городским масштабом.

Без ключа proxy завершается с явной ошибкой конфигурации, а endpoint сессии
карты возвращает понятный HTTP 503. Если карта временно не нужна, остальные
сервисы можно запустить отдельно:

```bash
docker compose up -d --build api postgres redis
```

Порт proxy по умолчанию доступен только на
`127.0.0.1:8088`; Angular dev-server пересылает туда `/map/**`.

Настройки cache по умолчанию: 2 ГБ, TTL 12 часов, `inactive=7d`. Cache хранится
в named volume `map_tiles_cache`. В access log proxy записывается только path:
API key, подпись и query string не журналируются. Смените signing secret, чтобы
немедленно инвалидировать все ранее выданные browser permissions.

Новые установки получают частичный индекс
`ix_buildings_map_coordinates (longitude, latitude)` автоматически при
создании таблиц. Поскольку Alembic до стабильного релиза не используется, для
существующей development database создайте индекс вручную без долгой блокировки
записи:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_buildings_map_coordinates
ON buildings (longitude, latitude)
WHERE longitude IS NOT NULL AND latitude IS NOT NULL;
```

Сравнить план bbox-запроса на 550 000 строк до и после индекса можно командой:

```bash
docker exec -i xarionix_postgres_test \
  psql -U xarionix_test -d xarionix_test \
  < tests/performance/map_buildings_explain.sql
```

Проверка proxy использует локальный HTTPS mock origin, проверяет подпись,
валидацию `z/x/y`, cache HIT, cache lock, отсутствие секретов в логах и 250
параллельных cache misses:

```bash
infrastructure/map-proxy/tests/run-proxy-tests.sh
```

Перед production-включением нужно подтвердить подходящий тариф и лицензионные
условия Yandex Maps для закрытой ERP. Текущие общие бесплатные условия требуют
открытого бесплатного доступа к приложению; 12-часовой cache технически
является временным, но его допустимость и коммерческое использование должны
быть подтверждены условиями вашего тарифа. В UI нельзя скрывать или перекрывать
логотип Яндекса, ссылку «Открыть в Картах» и ссылку на условия использования.

### Пользовательские маркеры

Маркеры хранятся отдельно от адресной иерархии в таблице `map_markers` и всегда
изолированы по `company_id`. При `sync_building_coordinates=false` необязательный
`building_id` является только информационной связью; координаты независимы.
При явном включении `sync_building_coordinates=true` точка маркера записывается
в дом. Дальнейшее изменение координат через маркер или карточку дома атомарно
обновляет дом и все синхронизированные с ним маркеры. Изменение только названия
или оформления не перемещает дом. Физическая точка дома общая для установки;
содержимое и оформление чужих маркеров по-прежнему недоступны. Это использует
существующее право `addresses.manage` на общий физический каталог.

Снятие связи или выключение синхронизации сохраняет последнюю точку маркера.
Удаление маркера не удаляет координаты дома. Очистка координат дома выключает
синхронизацию связанных маркеров, сохраняя их последние точки. При удалении
здания ссылка становится `NULL`, сам маркер сохраняется.

CRUD доступен по `/api/v1/map/markers`: чтение требует `addresses.read`, а
создание, изменение и удаление — `addresses.manage`. Иконки выбираются только
из серверного allowlist; произвольные HTML и SVG не принимаются. Цвета,
прозрачности, форма и размер проходят строгую Pydantic-валидацию.

Alembic до первого стабильного релиза по-прежнему не используется. Для новой
установки и существующей development database таблица создаётся идемпотентно
через `Base.metadata.create_all()` при следующем запуске обновлённого API:

```bash
docker compose up -d --build api
```

Операция аддитивная и не удаляет существующие данные. Перед обновлением
production-базы всё равно сделайте резервную копию и применяйте формальную DDL
миграцию согласно эксплуатационному процессу; `create_all()` не заменяет
версионированные миграции.

Для **существующей** таблицы перед запуском обновлённого API нужно применить
`infrastructure/database/map-marker-coordinate-sync.sql`: `create_all()` не
добавит колонку. В PowerShell (из корня backend-репозитория):

```powershell
Get-Content -Raw infrastructure/database/map-marker-coordinate-sync.sql |
  docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose up -d --build api
```

SQL идемпотентный и аддитивный. Старые метки получают `false`, их координаты
автоматически не меняются. В новой базе колонка создаётся с моделью.

### Данные сотрудника в приглашении и профиль

При создании приглашения можно передать необязательные `first_name`, `last_name`,
`middle_name` (каждое до 100 символов), `email`, `phone_number` и `date_of_birth`
(`YYYY-MM-DD`, не в будущем). Отчество не обязательно; имена не разбираются из
единой строки. В интерфейсе отображается «Имя Фамилия». Исторический `full_name`
сохранён без изменений и доступен в ответах только как запасное отображение;
в новых запросах создания это поле не принимается (422).
Пробелы в отдельных частях имени нормализуются, форматирование телефона убирается; допускаются
7–15 цифр и необязательный ведущий `+`. Код страны не угадывается. Email
проверяется на синтаксис без DNS-запросов и не является подтверждённым адресом
или новым способом входа. Письмо автоматически не отправляется: менеджер
по-прежнему передаёт одноразовую ссылку нужному сотруднику самостоятельно.

Данные хранятся в `company_invitations` и атомарно копируются в соответствующий
`CompanyMembership` при принятии ссылки. Глобальный `User` не содержит кадровых
данных компаний. При присоединении существующего пользователя другая компания
не может перезаписать его данные в прежнем членстве или дату создания аккаунта.
Публичный `POST /api/v1/invitations/resolve` не раскрывает персональные данные;
acceptance принимает только прежние учётные данные, не их замену клиентом.

`GET /api/v1/me/profile` требует JWT и текущего `X-Company-Id`, но не разрешения
на управление другими сотрудниками. Возвращается только собственный профиль
текущей компании: кадровые данные, `account_created_at` из `User.created_at` и
`joined_at` из `CompanyMembership.created_at`. Для нового пользователя это
момент принятия приглашения, не создания ссылки и не последующего JWT-login.
Для существующего пользователя дата глобального аккаунта сохраняется.
Просмотр данных других сотрудников остаётся под существующим company-scoped
`members.read`, создание/list/revoke приглашений — под `members.manage`.

Новые поля nullable: старые записи и приглашения остаются пригодными, отсутствующие
данные и исторические даты не выдумываются. Для существующей development database
перед пересборкой API выполните аддитивный SQL (таблицы не пересоздаются):

```powershell
Get-Content -Raw infrastructure/database/invitation-employee-details.sql |
  docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
Get-Content -Raw infrastructure/database/employee-structured-names.sql |
  docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose up -d --build --no-deps api
```

SQL идемпотентный; `create_all()` не добавляет эти колонки в старую базу.
Для production сначала сделайте резервную копию и примените DDL согласно
эксплуатационному процессу. Alembic в этом этапе не добавляется.
