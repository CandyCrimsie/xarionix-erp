# Рабочая область карты: слои, паспорта и предпочтения

Этап 2026-10-29. Базовый backend `7452d8f`, frontend `704bd7d`.
Это развитие существующей карты, не Stage 26. Сеть, адреса, геометрия,
классификация объектов, split и способы прокладки не заменяются.

## Подтверждённые причины и исправления

- Предыдущий bugfix уже устранил часть дублей ошибок удаления и основной метки.
  Гипотеза «редактирование всегда делает POST» не подтвердилась: редактор
  использует PATCH с ID и версией. Но поиск основной метки только в текущем
  отфильтрованном viewport действительно мог ошибочно считать её отсутствующей.
  Теперь действие оформления всегда проверяет `/map/buildings/{id}/marker`.
- Перепривязка самостоятельной `reference`/`located_at` раньше не запрашивала
  явное подтверждение старого и нового дома. Теперь используется тот же
  подписанный snapshot обеих сторон, а не только проверка основного оформления.
- Клик по объекту ранее загружал кабели независимо от фильтра отображения;
  скрытие не было выгрузкой. Чтение геометрии теперь управляется отдельным
  режимом, отменой запроса и поколением. Сохранять скрытый большой массив нельзя.
- Зависимости метки ранее читались полным графовым ответом. Теперь отдельный
  read-only endpoint возвращает группы и максимум 30 примеров, без геометрии.
  Окончательная проверка всё равно находится внутри DELETE.
- Карточка закрытого popup могла удерживать прежний выбранный объект/кабели.
  Обработчик реального закрытия очищает выбор; программное закрытие с явным
  сохранением выбора для вложенной формы обрабатывается отдельно.
- После завершённого редактора сохранялись draft/history и ссылки на линию.
  Завершённые/отменённые формы теперь освобождают их; активный draft не стирается
  скрытием: переключение режима сначала блокируется с понятным пояснением.
- Сортировка слоёв одинакового порядка через `sort_order ± 1` могла перескочить
  несколько соседей. `/layers/{id}/move` переставляет ровно одного соседа и
  нормализует порядок в одной транзакции с версией.
- В браузерном runner срок mock-сессии был задан через сотни лет. Переполнение
  setTimeout вызывало непрерывное `setTiles` и мешало дождаться загрузки подложки.
  Заглушка теперь выдаёт обычные 600 s; оба картографических компонента также
  ограничивают задержку максимальным 32-битным таймером. Proxy не меняется.
- Изолированные запуски старых map-тестов могли повторно использовать permission
  cache после пересоздания PostgreSQL ID. Map API/binding-тесты теперь явно
  используют существующий `clean_test_redis`; production RBAC не ослаблялся.

Не обнаружено оснований менять FK на CASCADE для сети, пересоединять кабели при
отвязке или удалять метки по совпадению координат. Такие действия не добавлены.

## Схема хранения

| Таблица | Назначение и ограничения |
|---|---|
| `map_layers` | Компания, название ≤120, группа-родитель, режим `group/manual/dynamic`, порядок, валидируемые rules JSONB, версия, timestamps. Составной FK родителя внутри компании; self-parent CHECK; циклы проверяются под company lock. |
| `map_layer_members` | Один из трёх настоящих FK: Building, MapMarker, MapConnection. CHECK ровно одного target, UNIQUE(layer,target), составные company FK к меткам/кабелям/слою. |
| `map_preferences` | PK(company,user), версия и settings JSONB со `schema_version=1`. Только настройки; никаких объектов, токенов, draft и паспортов. |
| `map_passports` | Компания и один типизированный FK; UNIQUE(company,target), версия, строго валидируемые данные JSONB. |

Удаление разрешённого целевого объекта удаляет **его метаданные** FK CASCADE;
удаление слоя удаляет только членства. Обратного каскада в адреса/сеть нет.
Удаление группы переносит её дочерние слои к родителю группы. Предел — 200
слоёв компании и 8 уровней. Режим существующего слоя не меняется, чтобы не
превратить ручные членства в незаметно игнорируемые записи.

У Buildings общий физический каталог — это существующая семантика проекта.
Паспорт и членства дома относятся к текущей компании. Основное оформление
`represents` использует членства дома, поэтому смена оформления не меняет слой
и не создаёт вторую логическую точку. Самостоятельные `reference/located_at`
имеют собственные членства и сохраняются независимо от дома.

## Состав и фильтрация

Порядок: доступ/JWT/company → OR включённых слоёв → AND остальных фильтров →
сортировка/лимит. SQL EXISTS не размножает точки при нескольких членствах.
«Без слоя» — отсутствие совпадений **со всеми** ручными и динамическими слоями,
а не отсутствие совпадения только с включёнными. Все слои выключены и «Без
слоя» выключено → пустой результат, не «показать всё».

Правила динамического слоя: `address_object_id` с реальными потомками,
`point_types`, `media`, `statuses`. Поля соединяются AND, значения поля OR.
Адресное правило для кабеля учитывает любой его конец, в том числе адрес дома
самостоятельной метки. Типы — любой конец кабеля. Среда/статус относятся только
к кабелям: слой с таким правилом не включает все точки по умолчанию.
Произвольных SQL/JSON-выражений и GIS-полигонов нет. Слой не предоставляет прав
и не меняет цвет кабеля.

У новых клиентов `layers_active=true`; старые клиенты без параметра сохраняют
старый нефильтрованный контракт. Добавлены bounded query parameters
`layer_ids`, `include_unassigned`, `point_types`, `point_types_enabled`,
`medium`, `status`, `installation`. Отдельный enabled-флаг отличает все типы
от явно пустого выбора. Matching остаётся в PostgreSQL до LIMIT.

Split и размещение на трассе копируют ручные членства исходного соединения
новому объекту, а split — также второму участку; версии слоёв обновляются в той
же транзакции. Первый участок сохраняет ID и паспорт, у нового отдельного
участка паспорт изначально пуст: инвентарные номера не копируются вслепую.
Динамический состав вычисляется по актуальным данным, не материализуется.

## API

Все пути под `/api/v1/map`, существующие JWT и `X-Company-Id` обязательны.
Чтение — `addresses.read`; слои/членства — `addresses.manage`. Паспорт личной
метки/линии также может изменять её владелец по существующему `require_write`.

| Метод и путь | Назначение |
|---|---|
| GET/POST `/layers` | Ограниченный список определений / создание |
| PATCH/DELETE `/layers/{id}` | Ожидаемая версия; удалить только организацию |
| POST `/layers/{id}/move` | `{expected_version,direction:-1\|1}`; атомарная перестановка соседей |
| PUT `/layers/{id}/members` | `{expected_version,target:{kind,id},present}` |
| GET `/objects/{kind}/{id}/layers` | Доступные членства без загрузки всего слоя |
| GET/PUT `/preferences` | Только текущие пользователь и компания; expected_version |
| GET/PUT `/passports/{kind}/{id}` | По запросу; версия паспорта и канонической сущности |
| GET `/objects/{kind}/{id}/dependencies` | Группы/количество/≤30 примеров, без геометрии |

DELETE метки/кабеля теперь принимает необязательный `expected_version` — старые
клиенты совместимы, новый UI отправляет версию. Коды конфликтов зависимостей
сохранены: `object_has_dependencies`, `endpoint_has_connections`,
`route_has_objects`, добавлена единая структурированная часть `dependencies`.
Приватные чужие зависимости обозначаются общей группой `restricted`, без
названий, владельцев, ID и количества закрытых записей.

## Удаление, связь и координаты

- **Привязать/перепривязать:** PATCH текущей метки; вторая запись не создаётся.
  Изменение существующей связи требует подтверждения snapshot старого/нового дома.
- **Отвязать:** редактирование с явным выбором допустимого типа при необходимости.
  Сохраняются дом, ID метки, её последняя позиция и кабели. Нет автоматического
  превращения дома в муфту и переподключения building endpoints к marker endpoints.
- **Удалить метку с карты:** удаляется только оформление/самостоятельная метка.
  Кабели, заканчивающиеся на этой самостоятельной метке, блокируют удаление.
  Кабель к Building не является кабелем к его `represents`-оформлению.
- **Удалить дом:** отдельное действие с отдельным подтверждением и обычными
  ограничениями адресного каталога; дом с кабелями/подъездами/помещениями не удаляется.
- Для ожидаемого конфликта зависимостей — ровно один общий Spartan Alert Dialog,
  без крестика, с кнопкой «Закрыть», backdrop/Escape/focus restore. Другие ошибки
  не подавляются. Предварительный read не заменяет проверку DELETE под блокировкой.

Координаты `represents` канонически принадлежат Building. Перемещение уже
расположенного дома явно подтверждается через `building_position`. Обычная
привязка самостоятельного оборудования не перемещает дом. Внутренние NULL
координаты основного оформления читаются через Building, а не считаются пропажей.

## Предпочтения и режим соединений

Settings сохраняются с debounce 300 ms, единственным запросом записи и очередью
последнего изменения; expected_version не позволяет старой вкладке перетереть
новую. При 409 требуется явное «Перечитать», при сетевой ошибке текущая работа
продолжается, без бесконечных toast. Удалённые ID слоёв отбрасываются, но
`include_unassigned=false` сохраняется. Неизвестная схема настроек безопасно
выключает данные с объяснением вместо скрытого включения всей карты.

Три режима:

- `hidden`: отмена HTTP и поколение загрузки, очищены коллекции, popup-ссылки,
  feature-state, индексы footprint, hit/halo/line GeoJSON, hover-плюс. Pan/zoom и
  обычный клик по объекту не читают геометрию. GC не обещается принудительно.
- `viewport`: свежая bbox-выборка с текущими фильтрами. Реальные сегменты,
  пересекающие область с обоими концами снаружи, сохраняются. Предел 2000 линий;
  при превышении явная ошибка `viewport_too_large`, не скрытое усечение.
- `object`: один шаг связей выбранного типизированного endpoint, а не обход сети.
  При смене выбора набор заменяется, при снятии очищается. «Показать связи» —
  явный переход в этот режим; действующие фильтры не сбрасываются.

Активный несохранённый редактор препятствует переключению режима. После успеха
или отмены завершённые draft освобождаются. Запросы и ошибки проверяют поколение
контекста/выбора; смена компании сначала очищает предыдущие данные и предпочтения.

## Паспорта

Загружаются только при открытии. Общие данные: инвентарный номер ≤80,
назначение ≤300, примечание ≤2000, дата ввода, состояние точки. Для дома — этажи
1–300 и помещений 0–100000; для опоры — высота >0 и ≤100 м; для шкафа — 1–100 U.
Прочие типы имеют общую секцию без выдуманного учёта портов и волокон.
Ноль отличается от отсутствующего значения.

Название/описание метки и название/описание/статус кабеля редактируются в
**существующей** сущности, а не дублируются в JSON. Среда, ёмкость/категория,
концы, длина, прокладка, адрес, координаты, компания и членства берутся из
существующих связей. Паспорт сам не редактирует геометрию; geometry_token от
изменения описания не меняется. Имя/описание требуют версии канонической записи,
метаданные — версии паспорта (0 для первого сохранения).
Если тип метки сменился, прежние дополнительные поля не стираются автоматически:
показывается notice, а новая форма требует осмысленного повторного сохранения.

## Безопасное обновление существующей development database

Не использовать `down -v`, удаление таблиц, blind pull или старую sync-миграцию
вместо этого этапа. API перед миграцией должен быть собран из нового кода.
Пример для текущего docker-compose из корня backend:

```bash
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/before-map-workspace.dump
docker compose build api
docker compose run --rm --no-deps api python -m database.map_workspace_upgrade --dry-run
docker compose run --rm --no-deps api python -m database.map_workspace_upgrade --apply
docker compose run --rm --no-deps api python -m database.map_workspace_upgrade --dry-run
docker compose up -d --no-deps api
docker compose logs --tail=50 api
```

Используйте новый уникальный путь backup, не перезаписывайте старый dump.
Сначала проверьте возможность восстановления копии в отдельную тестовую БД.
Postgres/Redis уже должны работать, чтобы `--no-deps` не запускал лишние сервисы.
У standalone Python те же команды запускаются из `app/` с окружением API.

Скрипт `app/database/map_workspace_upgrade.py` создаёт только четыре новые таблицы
с FK/CHECK/индексами, транзакционно, advisory lock 2517301 и lock_timeout 5 s.
Повторный apply безопасен. Старые ID, роли, координаты, геометрия и маршруты не
переписываются. Нужны права DDL/REFERENCES на существующие таблицы и CREATE в
схеме. Alembic/расширения не добавлены. Новая установка создаёт те же таблицы
через metadata. Автозапуск API также идемпотентно проверяет новую схему, но
эксплуатационная процедура выше позволяет увидеть dry-run до перезапуска.

Не предполагается ремонт произвольно частично созданных сторонним DDL таблиц:
dry-run проверяет наличие, а не сертифицирует чужую схему. Если найдено
несоответствие, остановитесь и сравните DDL. Обратный запуск старого кода не
требует удаления новых таблиц; откат DDL уничтожил бы новые паспорта/настройки,
поэтому универсальный destructive downgrade намеренно отсутствует.

## Проверки и ограничения

Основные backend-файлы:

- `app/models/map_workspace.py`, `app/schemas/map_workspace.py` — таблицы и строгие контракты.
- `app/database/map_workspace_upgrade.py`, `app/database/engine.py`,
  `app/models/__init__.py` — воспроизводимый additive DDL и регистрация моделей.
- `app/services/map_layers.py`, `map_preferences.py`, `map_passports.py` —
  состав/порядок/членства, версии персональных настроек и канонические паспорта.
- `app/api/v1/map_workspace.py`, `app/dependencies/map_filters.py`,
  `app/api/routers.py`, `app/api/v1/map.py` — защищённые endpoints/параметры.
- `app/repositories/addresses.py`, `app/repositories/map_markers.py`,
  `app/services/map.py`, `map_markers.py`, `map_connections.py`,
  `address_dependencies.py` — SQL-фильтры, привязка, bounded зависимости,
  версии DELETE и наследование членств в существующей транзакции.
- `tests/authorization/test_map_workspace.py` — новые PostgreSQL регрессии;
  `test_map_routes_api.py` — прежняя migration-регрессия теперь также убирает
  новые metadata FK при воспроизведении **старой** схемы и восстанавливает их.
- `tests/authorization/test_map_api.py`, `test_address_map_bugfix.py` — изоляция
  Redis между независимыми map-сценариями; ни один тест не отключён.
- `README.md` — актуальная семантика связей и ссылка на эту инструкцию.

Исходно: backend 562 теста, frontend 601 — успешно. Новые тесты используют
реальные PostgreSQL/Redis, включая параллельные независимые AsyncSession,
миграцию поверх старой схемы, реальные SQL-фильтры, private/RBAC, подтверждённую
перепривязку и rollback после вставки членств в split/place.

План на 1000 точках/20 членствах (PostgreSQL 18.6, тестовый контейнер): ручной
слой с LIMIT 10 дал ~1.3 ms, 32 shared hits, 0 reads; planner выбрал semi-join,
PK scan и materialized scan маленькой таблицы членств. Повторный замер — 1.43 ms;
без слоя — 0.031 ms, динамический типовой фильтр — 0.016 ms на том же наборе.
Это не обещание скорости
для миллионов объектов и не повод принуждать индекс. Индексы target/layer и
company/tree поддерживают lookup/FK; SQL-фильтр стоит до LIMIT. Повторить планы:

```bash
pytest -q -s tests/authorization/test_map_workspace.py::test_layer_query_plan_uses_real_postgresql_and_applies_filter_before_limit
pytest -vv
docker compose config --quiet
```

Браузерная проверка и изображения находятся в frontend:
`scripts/verify-map-workspace.mjs`, `docs/verification/map-workspace/`.
Запускает существующий Playwright runner с настоящим MapLibre/WebGL и локальными
API/raster fixtures, без нагрузки на Яндекс. DPR 1 — нейтральная схема; DPR 2 —
неоднородная спутникоподобная тестовая текстура, **не** живые спутниковые тайлы.
Остальные режимы старого runner не отключаются.

Результаты полного прогона и выбранные снимки перечислены в
`xarionix-web/docs/verification/map-workspace/README.md`.

Нет нового аудита, файлов/фото, пространственных полигонов, рекурсивного обхода
всего графа, PostGIS, новых кластеров/векторных тайлов. Камера не сохраняется в
предпочтениях: сохраняется текущая камера того же экземпляра при развёртывании.
Ограничения существующей bbox-модели у даталинии и при отсутствии координат
сохраняются; это не глобальная GIS-модель. Элементы Яндекса временно скрыты только
по debug-указанию; proxy/ключи/cache/rate limits не менялись.
