# Карта и адресные объекты: bugfix-аудит

База аудита: `0dbc0ee44d2bc8e68764d9563e13330472eff855` и локальное рабочее дерево frontend.
Изменений схемы PostgreSQL, миграций, FK или правил разрешений нет.

## Подтверждённые причины

1. Все причины запрета DELETE превращались в строку `Address record has dependent data`.
   Frontend одновременно записывал её в `actionError` и вызывал Sonner. Теперь сервер
   возвращает один структурированный доменный конфликт, а frontend открывает один Alert Dialog.
2. При выборе дома без координат редактор `represents` обнулял уже выбранную пользователем
   точку. Теперь frontend отличает явный выбор/ввод от начального центра карты и передаёт
   `building_position` через существующий канонический механизм.
3. Замена основного оформления корректно переводила предыдущую метку в `reference` в БД,
   но ответ mutation не содержал этого изменения. До следующего viewport frontend мог
   считать обе записи основными. Добавлены атомарные `binding_effects` в ответе.
4. Ранний выход при подавлении повторного центрирования не очищал `coordinateNotice`.
   Старый запрос bounds также мог обновить сообщение после смены выбора/сохранения.
   Frontend теперь инвалидирует запросы и очищает промежуточное состояние.
5. Создание соединения могло прочитать дом, проиграть гонку с его DELETE и вызвать
   `refresh()` удалённой ORM-записи: получался 500 вместо контролируемого 404.
   Концы перечитываются после блокировки, отсутствие записи проверяется явно.
6. `hlmAlertDialogAction` установленной версии Spartan NG — только оформление кнопки:
   подтверждение само не закрывалось. Frontend явно закрывает подтверждение и ждёт
   фактического освобождения overlay перед показом причин отказа.

## Контракт DELETE

Для адресного объекта, дома, подъезда и места размещения доменный отказ возвращает 409:

```json
{
  "detail": {
    "code": "object_has_dependencies",
    "message": "Невозможно удалить дом",
    "object": { "kind": "building", "id": 53 },
    "dependencies": [
      {
        "type": "map_connection", "count": 1, "has_more": false,
        "items": [{ "id": 128, "name": "Магистраль", "medium": "fiber",
          "source_name": "Узел A", "target_name": "г. Раменское, ул. Гагарина, д. 53" }]
      },
      { "type": "entrance", "count": 2 },
      { "type": "location", "count": 3 }
    ]
  }
}
```

Пример иллюстрирует схему; реальные значения берутся из PostgreSQL непосредственно
в DELETE, не из клиентского кеша. Для соединений возвращаются первые 30 доступных
записей, полный доступный `count` и `has_more`; для дочерних объектов — счётчики.
Другие типы групп: `address_object`, `building`, `equipment`, `restricted`, `integrity`.
Остальные HTTP-ошибки сохраняют обычную обработку. Клиентам, ожидающим строковый
`detail` именно для этого 409, необходимо перейти на `detail.code/message`.

### Приватность

Адреса/дома/подъезды общие. Locations ограничены текущей компанией. Соединения
дополнительно фильтруются существующим `visible_to(company_id, user_id)`.
Недоступная зависимость отображается только общим сообщением `restricted`:
без количества, ID, названий, концов линии, компании или владельца.
Подробный endpoint, позволяющий обойти эти фильтры, не добавлялся.

### Целостность и гонки

DELETE блокирует удаляемую запись `FOR UPDATE`, повторно проверяет зависимости
и сохраняет PostgreSQL FK RESTRICT последним барьером. При SQLSTATE 23001/23503
транзакция откатывается, причины перечитываются. `integrity` — безопасное пояснение
редкого FK-конфликта, когда после rollback уже нет перечислимой зависимости;
фиктивные записи в список не добавляются.

Занятый дом не удаляется и его метки не отвязываются. Дом без блокирующих данных
удаляется по существующей семантике: основные/самостоятельные метки сохраняются
с теми же ID, отвязываются, получают `none`; `represents` сохраняет последнюю
каноническую точку дома. Каскадное удаление кабелей не применяется.

## Контракт mutation метки

`MapMarkerResponse` дополнен необязательным для старых клиентов массивом
`binding_effects` (по умолчанию `[]`). Элемент содержит только `id`, `building_id`,
`building_link_role`, `latitude`, `longitude`, `version` изменённой прежней основной
метки. Это результат той же транзакции, а не дополнительная неатомарная запись.
Frontend применяет эффекты до обновления viewport. Все старые поля ответа сохранены.

Без изменений: PATCH сохраняет ID; bare `building_id` совместимо означает `reference`;
`reference/located_at` имеют собственную точку; `represents` читает точку из Building,
а не хранит её копию. Замена основной метки и перепривязка требуют существующего
snapshot-confirmation; UNIQUE, optimistic concurrency, company/private visibility
и блокировки `lock_map_company` остаются в силе.

## Неподтвердившиеся гипотезы

- Обычное редактирование не отправляло обязательный POST вместо PATCH или оба запроса.
  Реальный browser-тест проверяет PATCH прежнего ID и отсутствие POST.
- Само наличие `building_id` не превращает шкаф/оборудование в основной дом.
- Дедупликация не должна скрывать `reference/located_at` по совпадению координат.
  Это законные самостоятельные объекты. Прежняя основная метка после подтверждённой
  замены намеренно сохраняется как `reference`, а не удаляется.
